# Decisiones

## Cómo lo pensé

El contrato ya venía cerrado (`InventoryService`, `Reservation`, las excepciones, `StockAlertListener`), así que mi trabajo fue puramente la implementación. Fui construyendo todo de forma incremental con TDD: primero la tabla de reglas por categoría, después el registro de stock, el flujo básico de reservar/confirmar, el límite por pedido, la expiración, la idempotencia ante reintentos, las alertas de stock bajo, la concurrencia, y por último los casos borde que fui encontrando sobre la marcha. Cada paso quedó como un commit separado y con tests en verde antes de pasar al siguiente.

## Supuestos que tomé

- **Idempotencia de `reserve`**: el contexto dice que la app reenvía el pedido si la conexión es lenta, pero el contrato no dice qué debe pasar si `reserve` se llama dos veces con el mismo `orderId`. Decidí que un reintento con el mismo `orderId`, `sku` y cantidad devuelve la reserva ya existente (activa o ya confirmada) sin descontar de nuevo. Si el reintento llega con datos distintos (otro sku o cantidad), lo trato como un conflicto real y lanzo `IllegalStateException`. No se solicitó en el contrato, pero dejarlo sin resolver hubiera significado sobrevender cada vez que la red falla, que es justo el problema que el README quiere evitar.
- **Expiración perezosa**: las reservas no se liberan con un hilo en segundo plano. Se liberan solas la próxima vez que alguien consulta ese producto (`reserve`, `confirm`, `available`), comparando contra el `Clock` inyectado. Es más simple, no necesita infraestructura adicional, y el contrato ya estaba diseñado para esto al pedir un `Clock` como parámetro.
- **Umbral de stock bajo fijo en 5 unidades**: lo tomé literal de la tabla del README ("cuando a un producto le quedan 5 unidades disponibles o menos"). No lo hice configurable por categoría ni por producto ya que no se solicitó dentro de las validaciones actuales.
- **La alerta se resetea solo con `addStock`**: si el disponible sube porque una reserva expiró (no porque entró stock nuevo), no se vuelve a habilitar la alerta. Lo interpreté así porque el README dice explícitamente "no el mismo aviso repetido mientras el producto no se reabastezca", y una reserva vencida no es un reabastecimiento.
- **`registerProduct` llamado dos veces para el mismo SKU** reemplaza el producto anterior (se pierde el stock y el historial de reservas). El contrato no define este caso y no hay ningún test que lo ejercite, así que no quise inventar una regla de negocio (¿debería fusionar? ¿ignorar la segunda llamada? ¿lanzar una excepción?). Lo dejé como el comportamiento más simple y lo señalo acá en vez de realizar una nueva validación.
- **Concurrencia dentro de una sola instancia**: bloqueo por producto (`synchronized` en cada `Product`) para que dos reservas concurrentes del mismo SKU nunca sobrevendan. Cada SKU tiene su propio candado, así que reservar un producto nunca bloquea a otro. Lo probé con un test que lanza 300 reservas en paralelo contra 100 unidades de stock y verifica que exactamente 100 tengan éxito.

## Lo que dejé fuera a propósito

- **Capa HTTP / API REST**: el servicio es una librería Java consumida directamente a través del contrato (`Inventory.create`), tal como describe el README. No agregué Spring Boot, controladores ni una colección de Postman porque no hay ningún endpoint que exponer — hubiera sido alcance no pedido y una dependencia nueva sin justificación real.
- **Circuit breaker / retry con librería (Resilience4j, etc.)**: no hay ninguna llamada de red o a un sistema externo en este servicio. El único borde real es el `StockAlertListener`, y ahí apliqué solo lo proporcional: aislar la llamada en un `try/catch` para que un canal de notificación roto nunca tumbe una reserva que ya se hizo. Meter un circuit breaker completo (con estados open/half-open) para una llamada local y síncrona hubiera sido sobre-ingeniería.
- **Scheduler para expirar reservas**: como expliqué arriba, la expiración es perezosa. No hay ningún hilo corriendo en segundo plano.
- **Persistencia / capa de repositorio**: el README dice explícitamente que por ahora los datos pueden vivir en memoria. No armé una abstracción de `Repository` "por si acaso" se migra a base de datos — hubiera sido generalidad especulativa sin un caso de uso presente.
- **Purga de reservas confirmadas y del índice `orderId → sku`**: ambos crecen indefinidamente mientras el proceso esté vivo, porque los necesito para que la idempotencia funcione en cualquier momento después de confirmar un pedido. Para esta prueba (proceso de vida corta, datos en memoria) no lo veo como un problema real, pero lo anoto abajo porque en producción sí lo sería.

## Qué cambiaría antes de llevar esto a producción

- **Concurrencia multi-instancia**: el `synchronized` por producto garantiza correctitud dentro de una sola JVM, pero el README menciona que el servicio va a correr en varias instancias con los datos en una base de datos. Ahí el lock en memoria no serviría — necesitaría locking optimista (una columna de versión) o `SELECT ... FOR UPDATE` a nivel de fila en la tabla de stock, y mover el índice `orderId → sku` a esa misma base de datos con una restricción única sobre `orderId`.
- **Purga de datos históricos**: movería las reservas confirmadas y el índice de pedidos a almacenamiento persistente con una política de retención (por ejemplo, conservar solo lo necesario para soportar reintentos dentro de una ventana razonable, y archivar o eliminar el resto), en vez de mantenerlo todo en memoria para siempre.
- **Definir qué pasa si se re-registra un producto existente**: hoy lo reemplaza en silencio. Antes de producción, hablaría con el equipo de negocio para decidir si debería ser un no-op, una actualización de categoría sin tocar el stock, o un error explícito.
- **Canales de notificación adicionales**: el README menciona que las alertas hoy van por correo y a futuro se van a expandir a más canales. Hoy `StockAlertListener` ya permite eso sin cambios (es quien implemente la interfaz el que decide a dónde mandar el aviso), pero si en el futuro hay varios canales simultáneos y alguno empieza a fallar de forma sostenida (no solo una excepción puntual), ahí sí consideraría un circuit breaker real para dejar de intentar ese canal temporalmente, en vez de solo capturar la excepción como hago ahora.
- **Observabilidad**: no agregué logging estructurado ni métricas (por ejemplo, cuántas reservas expiran sin confirmarse, o con qué frecuencia se dispara el stock bajo) porque no había una librería de logging ya elegida en el proyecto y no quise imponer una. En un entorno real, esto sería de lo primero que agregaría.
